# m68k-os9-l68

`m68k-os9-l68` is a drop-in for Microware's linker `l68`, taking the options of both C 3.2's and
Ultra C's, and writing the modules they write, for every module type. It links with GNU `ld` and
makes the module with [elf2mod](elf2mod.md); ROF objects and libraries are converted with
[rof2elf](rof2elf.md) on the way. [m68k-os9-xcc](m68k-os9-xcc.md) links through it, as C 3.2's
`xcc` runs `l68`, and [m68k-os9-gcc](m68k-os9-gcc.md) links through the same code.

    m68k-os9-l68 cstart.r prog.r -l=clib.l -l=sys.l -o=prog -g    # prog and prog.stb
    m68k-os9-l68 desc.r -o=term                                   # a device descriptor

## Usage

    m68k-os9-l68 [options] <files>...

The two Microware linkers' options don't clash: where both have a letter it means the same, and
Ultra C's set extends C 3.2's, so the union is accepted, without a mode option. Case matters, as
in both (`m`/`M`, `o`/`O`, `s`/`S`, `r`/`R` are different options), except that C 3.2's `-E=<n>`
is `-e=<n>`.

| Option | Meaning | Here |
|---|---|---|
| `-a` | far `bsr`/`lea` through the jump table | the jump table `elf2mod` builds (see "The jump table"); without `-a`, an error where one is needed |
| `-b=<n>` | align code and data to `<n>` (Ultra C) | see "Alignment" |
| `-c` | ANSI: only the underscored linker symbols (Ultra C) | the plain `btext`, `bname`, `etext`, `bdata` and `end` left out |
| `-e=<n>`, `-E=<n>` | module edition | the last one given; a global `_sysedit` wins (see "Linker symbols") |
| `-f=<perms>` | file permissions (Ultra C) | ignored: no OS-9 file attributes on the host |
| `-g` | a symbol module for the debugger, and a `.dbg` file for psects with source debug information | see "Symbol modules" |
| `-gu=<g>.<u>` | owner (Ultra C) | the module's owner |
| `-i` | initialized static storage in a system module (Ultra C) | as Ultra C's (see "Module layouts") |
| `-j` | print the jump table map | prints the entries `elf2mod` made |
| `-l=<path>` | a library, searched after all files | ROF (concatenated), `libgen`'s format, or `ar`, told apart by content |
| `-m[=<path>]`, `-s[=<path>]`, `-w` | module map, with symbols, alphabetical | GNU `ld`'s map, to the path or standard output |
| `-M=<n>[K]` | more stack, in KB | added to the stack |
| `-mt<x>` | thread-incompatible code (Ultra C) | accepted, no effect |
| `-n=<name>` | module name | the last one given (see "Output and names") |
| `-o=<path>`, `-O=<path>` | output, in the execution or data directory | the path as given |
| `-p=<hex>` | module header permissions | the same |
| `-r[=<base>]` | raw binary, the code at `<base>` | see "Raw output" |
| `-R=<n>` | revision (Ultra C) | the same; a global `_sysattr` wins |
| `-S` | sticky module | the attribute's sticky bit, on top of the psect's attributes |
| `-t=<target>` | target (Ultra C) | `os9_68k` only (the OS-9000 targets are errors); also Ultra C's symbol module format |
| `-v` | verbose (Ultra C) | prints the commands run |
| `-x=<n>` | align the execution offset to `<n>` (Ultra C) | the code start in the module aligned, zero fill |
| `-z[=<path>]` | files and options from `<path>` or standard input | the same: one argument per line, blank lines and lines starting with `*` skipped |
| `-N[=<name>]` | ours | the module name after the contents (see "Output and names") |
| `-dialect=ucc\|c32` | ours | the order of library members: Ultra C's `l68`'s (the default) or C 3.2's (see "Library members") |
| `-namepad=<hex>` | ours | the byte after an odd-length module name (default 00): native OS-9 builds of `l68` copy the name in words, so their pad is the next character of the command line |
| `-stbnamepad=<hex>` | ours | with `-g`: the byte after the symbol module's odd-length name, which `l68` leaves as it happens to be (default 00) |
| `-dbgversion=<n>` | ours | with `-g`: the `.dbg` file's word after the magic (default: 3 in Ultra C's format, 0 in C 3.2's; older Ultra C files have 1) |
| `-jmptblpad=<n>` | ours | with `-a`: `<n>` unused entries (`jmp 0`) after the used ones, as some of Ultra C's links have them |
| `-irefspad=<hex>` | ours | bytes after the initialized data's pointer tables, before the CRC, as some old modules have |
| `-gnu-prefix=<p>`, `-elf-*` | ours | where the GNU tools are, and the ROF conversion's settings (see [m68k-os9-xcc.md](m68k-os9-xcc.md)) |

`-?` prints the usage: `l68`'s options in Ultra C's `l68 -?` order, each with what differs in
square brackets, then our own options and the environment (`GRPUSER`, `M68K_OS9_ELF`,
`M68K_OS9_GNU_PREFIX`), from the parser's own table of options.

## Inputs and libraries

The files are taken in order; ROF objects are converted (with the conversion cache and settings
of [m68k-os9-xcc.md](m68k-os9-xcc.md)), ELF objects used as they are, whatever their suffix.

- **The root psect,** the one with a module type (normally `cstart.r`'s), gives the module header
  through its `__os9_*` symbols. None is an error ("no root psect found"), and so are two ("root
  psect found in both"), as in `l68`.
- **`-l=` libraries** are searched after all files, wherever they stand on the line, in one pass
  in their order: a library satisfies its own later members, but a name only an earlier library
  defines stays unresolved, as in `l68`. One ROF object given as `-l=` is a library of one member,
  as C 3.2's `l68` takes it.
- **A library given as a plain file** is linked whole, unused members included, as `l68` links a
  concatenated `.l` given so; also an `ar` archive, and a `libgen` library (which `l68` refuses
  as a file).

### Library members

The two Microware linkers take the members they need from searched libraries in different orders,
and the module then has the same code at other addresses:

- **C 3.2's `l68`:** in the library's own order, searching it once.
- **Ultra C's `l68`:** the libraries one by one, in command-line order. In each, the names still
  unresolved, in order (the objects' first, in command-line order and each object's in name order,
  then those of members linked from earlier libraries), each links the member of this library that
  defines it; a member linked stacks the members of the same library defining its unresolved
  references (in name order, link-time expressions' terms included), and the top of the stack is
  linked next. So within a library the members are taken depth-first, the most recently stacked
  one next.

They also choose differently where several members define a name: Ultra C's `l68` takes the first
one in the library it is searching when the name is unresolved; C 3.2's `l68` the first after the
member that refers to it. A library with a dummy definition after the real one links with C 3.2's
and fails with Ultra C's when the real one needs what the link lacks.

`-dialect=ucc` (the default) follows Ultra C's: the libraries' members are extracted, their
symbols read, chosen by these rules and given to `ld` as objects in that order. `-dialect=c32`
gives `ld` the libraries, whose search keeps the archive's order; `m68k-os9-xcc` passes it.

### Duplicate symbols

Both Microware linkers agree:

| Case | `l68` |
|---|---|
| two objects, the same equate (any value) or code label | error |
| an object and a library member **with code or data**, taken in, any duplicate | error |
| an object and a library member **with equates only**, taken in for another symbol | links: the object's value |
| two library members with equates only, both taken in, the same equate | links: the first member's value |
| a library member whose symbols the objects already define | not taken in, no error |

GNU `ld` refuses the two cases that link, so each library is linked as a copy in which the global
symbols of members that define only equates are weak: a strong definition (an object's) wins, and
among weak ones the first, as in `l68`. This lets a driver link with `sys.l` and a library of
equates of its own.

## Output and names

Without `-o=`/`-O=` the output is the file `output`, holding the module `output`, as with `l68`;
of several `-o=`/`-O=`, and of several `-n=`, the last counts. Without `-n=` the module is named
after the output file, a final lower-case `.mod` dropped (see "Module names" in
[m68k-os9-xcc.md](m68k-os9-xcc.md)), where `l68` keeps the name as given.

`-N=<name>` sets the name and puts it after the contents; a bare `-N` puts the name it would have
there. Between `-n=` and `-N=` the last name given counts, and `-N` anywhere puts it last. On
module types whose name already follows the contents it changes nothing. (Microware's tools have
no such option; `m68k-os9-gcc` passes it to `elf2mod` as `-Wm,-N`.)

The defaults are `l68`'s: header permissions `$0555`, and for a link without a root psect's
values, type/language `$0101` and attributes/revision `$8001`. The owner comes from `GRPUSER` or
`-gu=`; without either it is 0.0, where both Microware linkers make 1.0.

## Module layouts

The module type and language decide the layout, as in both Microware linkers (their layouts
differ from the table in the OS-9 Technical Manual):

| Type and language | Fields after `$30` | Name |
|---|---|---|
| program (`$01`),<br>trap library (`$0B`);<br>language 1 | the program header: `M$Exec`, `M$Excpt`, `M$Mem`, `M$Stack`, `M$IData`, `M$IRefs` (`$30`-`$47`); the code at `$48` | after the header |
| any other type:<br>system module, file manager,<br>driver, data, descriptor,<br>subroutine;<br>language 1 | `M$Exec` (the entry, or the contents' start `$3C`), `M$Excpt` 0, `M$Mem` (the vsect size), even without entry or vsect | after the contents |
| language 0:<br>`$0400`, `$0F00`, `$0C00` | none: the contents at `$30` | after the contents |
| system module (`$0C`)<br>with `-i` (Ultra C);<br>either language | the program header, type `$0C` | after the header |

- Trap libraries get no `M$Init`/`M$Term`, as `l68` writes them.
- A `vsect` with language 0 is refused ("no data storage allocation (vsect) allowed on non-object
  modules"), and initialized data (also a jump table) on every type but programs, trap libraries
  and `-i` system modules ("initialized data (or jumptable) allowed only on program or trap handler
  modules"), as in `l68`. A data module or descriptor written for the kernel's layout should be
  language 0.
- With `-i`, the kernel doesn't initialize the data: the module does it from `M$IData`/`M$IRefs`.
  Programs and trap libraries are the same with and without `-i`.
- **Data addressing:** `l68` biases a6-relative data offsets by `$8000` (`cstart.r` sets a6 so)
  only for programs and trap libraries; every other type, and raw output, addresses its static
  storage from its start (`lea v(a6),a0` gives `$0004`, not `$8004`).
- **Values without a field are errors** here: a stack, an entry point or `-M=` that the module
  type has no field for, or a `vsect` or entry with a header without fields. `l68` drops them
  silently; this catches mistakes. A value that is zero counts as absent (a ROF always has a
  stack and entry, 0 for a data psect), and without `M$Stack` there is no default stack.

### Alignment

`-x=<n>` aligns the code start in the module (`-x=4` moves it from `$4E` to `$50`), zero fill; on a
trap library the code stays at `$48` and the padding goes after the name instead. `-b=<n>` pads
each psect's code and data to a multiple of `<n>`: in Ultra C's format (`-t=`) with `<n>` above 2,
counted from the start of their section, as Ultra C's `l68` pads the psects' sizes; otherwise each
psect is aligned.

### Raw output

`-r[=<base>]` writes the module's body without header, name and CRC (the code, then the initialized
data block and the pointer tables), linked with the code at `<base>`, and prints the code and data
sizes. `-g` still writes a symbol module. It defines `dsize`/`_dsize`, `_bidata` and
`edata`/`_birefs` besides the other linker symbols.

## Linker symbols

The link defines `btext`, `bname`, `etext`, `bdata` and `end`, and the underscored `_btext`,
`_bname`, `_etext`, `_bdata` and `_enddata` (Ultra C's `acstart.r` needs `_enddata`), in both
formats; `-c` leaves out the plain ones, as Ultra C's `l68` does. See also "The linker's module
symbols" in [elf2mod.md](elf2mod.md).

- **`etext`** is the module's size, plus 4 when exactly one of the two pointer tables (pointers to
  code, pointers to data) has entries, as both Microware linkers write it.
- **`bname`, `btext`, `etext` in the code as absolute values** (`dc.w bname` in a descriptor) are
  their offsets in the module, as a code label's address is.
- **`_sysedit` and `_sysattr`:** a global of either name in any object (a C file's `@_sysedit: equ
  7`) gives the module's edition, or its attributes and revision, over the root psect's and over
  `-e=` and `-R=`.

## References

- **A non-PC-relative reference to a code label** holds the label's offset in the module: in the
  code (`dc.w Init` in a driver's entry table) as it is, in the initialized data (`dc.l`) with an
  entry in the module's table of code pointers, relocated by OS-9 when the module is loaded.
- **A PC-relative reference to an absolute symbol** (`bsr EQU`, `lea EQU(pc),a0`) is an error, with
  `l68`'s message ("relative reference to symbol 'X' in the absolute (equ) area").
- **Link-time expressions:** `l68` resolves a reference that adds and subtracts several externals
  (`Dir_+Write_`, `-E$Abort`), as r68 makes them for `sys.l`'s equates. `rof2elf` and `r68togas`
  make such a field refer to a symbol `r68x_<hash>` (the 32-bit FNV-1a hash of the expression's
  canonical text, its terms sorted by name) and note its definition in the object's section
  `.r68x`. When a link fails with undefined `r68x_` symbols, the front end takes the notes of the
  objects and members actually linked from a link written anyway, defines each symbol in a linker
  script (`NAME = "Dir_" + "Write_";`, the terms also given to `ld` as undefined so that `sys.l`'s
  members are taken in), and links again; `ld` checks that each value fits its field. A link
  without such references costs nothing more.

## The jump table

A program with more than 32 KB of code can't reach every function with 16-bit calls. With `-a`, it
is linked again with a jump table, which [elf2mod](elf2mod.md) builds and fills (see "Far calls"
there). The entries are in Ultra C's `l68`'s order: by the object of a target's first far
reference, in link order; among one object's new targets, those the files given define first, then
those of the `-l=` libraries in their order; then by name. Within one source file of more than
32 KB of code the assembler resolves the calls itself and fails; such a file has to be split.

## The pointer tables

The initialized data's pointer tables (`M$IRefs`: the pointers to the code, then those to the
data) list first the jump table's entries, in reverse order; then the pointers object by object,
in reverse link order. Within an object: vsect by vsect in the
source's order, each vsect's in address order (a remote vsect first); then its pointers to other
objects' globals, by name in descending order, and for one name by address, descending. `elf2mod`
writes them so from `ld`'s map and the objects' reference order records (written by `r68togas`
and `rof2elf`).

## Symbol modules

`-g` writes the symbol module (`<output>.stb`) and, where psects have source debug information
(C 3.2's `c68 -g`), the `.dbg` file; see "Symbol modules for the debugger" in
[elf2mod.md](elf2mod.md). Its format follows `-t=`, which Ultra C's `xcc` always passes and C 3.2's
`l68` doesn't know: Ultra C's format with `-t=`, C 3.2's without. In Ultra C's format the
program's symbols come before the linker's at the same value.

## How it works

The front end decides from type, language, `-i` and format what `l68` would write, and refuses
what `l68` refuses; `elf2mod` stays type-agnostic and is told the layout:

| Need | `elf2mod` option |
|---|---|
| header permissions, sticky | `-p HEX`, `-S` |
| name after the contents | `-N[NAME]` |
| type/language word | `--typelang=HEX` |
| header size | `--header=0x30\|0x3C\|0x48` |
| code start alignment | `-x N` |
| raw output | `--raw` |
| no entry point | `--entry=none` |

The linker script places the data area for the type's bias, defines the linker symbols, aligns or
pads for `-b=`, and links at `<base>` for `-r`.

## Microware compatibility

The modules are compared byte for byte with Ultra C's `l68` and C 3.2's `l68` on the same ROF
objects: the whole type and language matrix (program, trap library, `-i` system module, language 0
data, descriptor and system modules, language 1 data, system, file manager, driver and subroutine
modules, each with and without an entry point and a `vsect`), `-e=`, `-E=`, `-R=`, `-S`, `-p=`,
`-gu=`, `-M=`, `-c`, `-x=`, `-b=`, `-z`, the default output and names, and the symbol modules;
and through more than 1,100 modules rebuilt from real sources and compared with the originals.

## Differences and limitations

- **The owner** is 0.0 without `GRPUSER` and `-gu=`, where both Microware linkers make 1.0.
- **A root psect that isn't first** gets the right entry point; `l68` accepts it but points
  `M$Exec` at the first psect.
- **The symbol module's header parity** is at `M$Parity` (`$2E`) in both formats; Ultra C's
  `l68` writes it at `$28` and leaves `M$Parity` zero, so in Ultra C's format the `.stb` files
  differ in those bytes.
- **Values without a field** are errors (see "Module layouts"), where `l68` drops them.
- **Library members C 3.2's `l68` doesn't find:** it searches a library once, so a member needed
  only by a member further on is unresolved there; `ld` searches the archive again, so the link
  works here.
- **The pointer tables within a GCC object** are in address order (GCC writes no reference order
  records); both Microware linkers list them vsect by vsect, which only matters with remote data
  first.
- **A `dc.w` of a code label in the initialized data** is refused: both Microware linkers give it a
  table entry, and OS-9 then relocates a longword there, corrupting the field.

## Tests

- **`tests/r68`**: cases for the linker (`l68-*`): library member order and choice, libraries given
  as files and as one ROF, duplicate equates, link-time expressions and the linker symbols, the
  pointer tables' order, the jump table's order and `-jmptblpad`, `-b=` padding, raw symbols,
  `_sysedit`, PC-relative references to equates, name and `M$IRefs` padding, symbol modules and
  `.dbg` files; with `R68` set, several compare with Ultra C's tools.
- **`test/l68cmp`** in the superproject: links compared byte for byte with Microware's `l68`.
- **`test/abi-exec`**: `make check-l68` (the tests linked by Microware's `l68` through `elf2rof`
  and run in the test harness's 68000 emulator), `check-mod` and `check-lsym`; its OS-9 targets run
  linked modules on a real CD-i 605 and on CD-i Emulator's.
